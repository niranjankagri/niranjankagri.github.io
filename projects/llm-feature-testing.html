Problem and purpose

Shows how to test a feature whose output is phrased differently every time, varies between runs and can be talked into misbehaving. The companion project uses AI to write tests; this one tests an AI feature, and tests the tests: the eval data, every check and the judge are verified before any model result is trusted.

My contribution

I built and maintain this public project, including the framework or test harness, its documentation, and the execution evidence linked here.

Architecture

evals/cases.json (32 cases x 3 samples)
      │

      ▼

      ▼

Engineering decisions and tradeoffs

  • Testability starts in the feature: a structured reply makes outcome and citations exact checks
  • A fictional policy, so the model cannot answer from general knowledge and the eval shows whether it reads its source
  • The assistant never receives colleagues' data; the leak check looks for their real dates in four formats
  • A canary string in the system prompt makes instruction leaks detectable with a substring check
  • Cheap deterministic checks first; the judge is only paid for answers that already passed them
  • The eval data is tested: every hand-written reference answer must pass, and a refuse-everything model cannot pass the set

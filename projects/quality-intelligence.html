Problem and purpose

Each automation framework reports on its own run, but a release decision needs answers across all of them: which requirements are tested, which critical ones have no automated test, what failed and what it puts at risk, which tests are flaky, and whether this build meets the agreed criteria. This platform answers those questions from the results the frameworks already write. Execution history comes from collected CI result files, while the requirement catalog used by the demonstration is synthetic; the two data sources are kept distinct.

Engineering decisions and approach

  • Coverage and pass rate are separate numbers, never one blended score; a zero denominator is shown as n/a, not 0 % or 100 %
  • A gate has three outcomes with their own exit codes: passed (0), failed (1), incomplete (3); missing, broken or empty results can never pass
  • Business logic never imports the dashboard; a test parses every import and fails the build otherwise
  • Flaky candidates only by written rules with evidence: the strongest one is a test that passed and failed on the same build
  • Duration regressions need two slow runs in a row, after one noisy run in a parallel suite flagged 19 tests
  • Real CI result files as sample data (sanitised), so ingestion is proven on what frameworks really write
  • Cypress and Allure adapters produce the same model as JUnit XML; one CI job that writes both Allure and JUnit is compared test by test
  • A security review by probing with hostile files: eight findings fixed (e.g. a UTF-16 XML file bypassed the entity check), each now a test

Problem, decision and result

Problem

Results spread across repositories make release readiness difficult to inspect.

Decision

Normalize existing result files, retain execution context, and keep collected CI evidence separate from the synthetic requirement catalogue.

Test scope and execution approach

Project-specific checks and execution details documented in the repository:

  • Imports 43 real result files from four producers; the counts match each file's own totals
  • Requirement coverage, automation coverage and automated requirement coverage, with gaps and breakdowns by feature, criticality, test type and platform
  • Execution history: stability classes with evidence, recurring failures, duration regressions, trends, run comparison
  • Cypress (mochawesome JSON or HTML) and Allure results folders import into the same model: 8 real Cypress runs and 5 Allure runs, each Allure run matching the JUnit XML of the same job
  • Collects real CI results every day from four public automation repositories (enterprise TestNG, pytest, Cypress, Robot Framework) out of their workflow artifacts: on 20 Oct 2026, 22 pipeline runs and 3,792 test results, each job count matching the producer's own CI log, and a cancelled run recorded as incomplete
  • CI pipeline executions: the jobs of one run are grouped (re-run attempts, branch, commit); a gate never decides on a pipeline with a missing job. Shown on a real TaskBoard run whose Firefox job was cancelled: 114 of 114 existing results passed, the gate says incomplete
  • Requirements imported from a CSV export (preview, row-level errors, no duplicates on re-import); test-case links are never touched
  • A live report: overview with four separate headline figures (pass rate, automation coverage, critical gaps, release readiness), test results by repository, job and class, failures grouped by cause, trends, and coverage by product and feature; filters offer only combinations that were recorded, and every figure opens its evidence
  • Test details open the exact execution that was clicked (repository, job, browser, run) with its history in that context, a browser comparison and the evidence; missing data is said to be missing: no results is never 100 %, a missing duration is never zero
  • Release readiness as a scorecard: every criterion with its measured value, threshold, result and effect, each linked to its evidence; the release gate per day and the days its reasons changed
  • Recurring failures ranked by how often they failed in the last 7 days, latest regressions per suite and branch, coverage gaps by criticality and owner, a daily digest, and issue drafts that a person submits through GitHub's own form (nothing is created automatically)
  • A historical test execution dashboard: all recorded executions, daily outcomes and the slowest, most failing and most erroring tests per execution context
  • The original dashboard with requirements, tests, runs, pipelines, stability and trends pages remains available; trend values checked against the stored records with plain SQL; filters kept in the address
  • Quality gate reports in JSON, HTML and Markdown (GitHub job summary)
  • Gates its own release on the project plan's ten acceptance criteria, using its own test results

Workflow and reports

Scheduled collection reads existing workflow artifacts. The visitor page does not poll repository APIs; the Render service is periodically refreshed and retains its last collected snapshot. Each deployment is smoke-tested over HTTP and in a browser.

Known limitations

  • Three input formats (JUnit XML, mochawesome, Allure results); mochawesome records no browser, build or retries, so those are given on the command line
  • Tests are identified by name: renaming a test starts a new history
  • The dashboard login is one shared account (basic authentication): for a team, put TLS or the organisation's login proxy in front
  • The requirement catalog in the demonstration is synthetic; the test results are real
  • The requirement catalog is synthetic; collected CI results are real. The shared dashboard account is documented in the case study.

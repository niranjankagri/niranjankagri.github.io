Integration Testing with Testcontainers (Kafka, GraphQL)

How I test an event-driven service against its real dependencies: every run starts PostgreSQL and Kafka in Docker with Testcontainers, and the tests talk to the service the way its clients do, over GraphQL and Kafka. The service is deliberately small; the point is the test design.

View source code View documentation View latest CI runs View test report

Purpose

Between unit tests and end-to-end tests sits the layer where many production bugs live: a migration that fails on the real database, an event with a wrong field, a consumer that stalls on one bad message. This project tests exactly that layer, with real infrastructure per run instead of mocks, an in-memory database or a shared test environment.

Technology stack

Architecture overview

test ──GraphQL/HTTP──► order service ──► PostgreSQL 18 (container)
                          │  ▲
          orders.placed ◄─┘  └── payments.completed ◄── test (KafkaTemplate)
                                    │ failures
                                    ▼
                          payments.completed.DLT ──► test probe

Key engineering decisions

  • Real PostgreSQL and Kafka, because H2 and mocked brokers hide exactly what breaks: SQL dialect, constraints, partitions, redelivery
  • One cached Spring context for every test class, so the containers start once per run
  • Unique data per test instead of cleanup: no order dependence, ready for parallel runs
  • Awaitility polls for the expected state; absence is proven by waiting for a later event on the same partition
  • Idempotent consumer: event id recorded in the same transaction as the change

Implemented features

  • Migrations and check constraints tested on the real database
  • GraphQL: queries, the mutation, BAD_REQUEST validation errors, schema rejections, null propagation
  • Events: OrderPlaced published after commit and keyed by order id; duplicates applied once; broken, incomplete and unknown-order events dead-lettered without blocking
  • Found that Spring Kafka 4 renamed the default dead-letter topic; the name is now explicit
  • A mutation check revealed an untested retry rule; a unit test now covers it
  • Design notes and 60 interview questions on integration testing, Kafka and GraphQL (Markdown + PDF)

Setup and execution

mvnw.cmd verify                 :: 21 tests with real containers (Docker needed)
mvnw.cmd spring-boot:test-run   :: the service with the same containers, GraphiQL at /graphiql

CI workflow

On every push: the full suite on GitHub's Ubuntu runner, which has Docker, so the containers start exactly as on a laptop. The job summary lists each test class with its counts and time.

Known limitations and future improvements

Limitations

  • OrderPlaced is sent after the commit; a crash in between would lose it (production would use a transactional outbox)
  • One service: contracts between producer and consumer teams are shown in the Pact project

Next steps

  • A transactional outbox with a crash test
  • Consumer performance and rebalancing tests

Problem and purpose

As a test engineer I test backends every day; this course is the other side: building them. I kept it to the same standard as my test frameworks: a README per topic, tests for every example, CI on two JDKs, and a real deployment at the end. The Airbnb backend (Sessions 21 to 24) is live at airbnb-backend-u7lv.onrender.com; it is an API, so it is used with curl or Postman.

Engineering decisions and approach

  • Double bookings are stopped twice: a locking read in the service and a PostgreSQL exclusion constraint on the date ranges, so even a race between two servers ends in 409
  • The image that is deployed is the image that passed the smoke test in CI; Render deploys main only after its checks pass
  • Readiness decides when a new version gets traffic; health endpoints are open, everything else needs a login
  • Errors are Problem Details (400 with field errors, 401, 403, 404, 409)
  • One module per session, so each topic builds and tests on its own

Test scope and execution approach

Project-specific checks and execution details documented in the repository:

  • Two projects grown over several sessions: Splitwise (Sessions 12, 13, 17) and Airbnb (21 to 24)
  • Airbnb: listings with search by city, dates, guests and price; bookings and cancellation; reviews after a stay; host notifications after commit
  • Microservices with Feign and client-side load balancing; messaging and resilience
  • AI sessions: prompt experiments, spec-driven development with generated acceptance tests, and a RAG course assistant with only the JDK
  • A smoke test script that checks any running deployment through its API

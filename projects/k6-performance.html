Problem and purpose

Shows how I approach performance testing: one test per question, pass/fail criteria agreed up front, realistic workload models, and results that lead to a fix. The app under test, a small shop API, is part of the repository, so the tests never put load on someone else's server and every CI job measures its own copy.

Architecture

k6/tests/*.js     scenarios (who, how many, which executor) + thresholds (SLOs)
      │
k6/lib/flows.js   journeys browse() and buy(): checks, think time, business metrics
k6/lib/api.js     one function per endpoint, stable name tag per request
k6/lib/config.js  BASE_URL, PROFILE (ci | full), THINK
      │
QuickShop (app/)  started by each CI job; checkout limited by 8 "database connections"

Engineering decisions and approach

  • SLOs per endpoint as thresholds (p95 per endpoint, error rate, checks, business metrics): a missed SLO exits with 99 and fails the job
  • Visitors in a closed model (ramping-vus) and orders in an open model (arrival rate) in the same test; dropped iterations have a threshold
  • One login per virtual user, a different test user per VU from a SharedArray, random think time
  • Each test has a ci size for every push and a full size for a dedicated environment, side by side in the script
  • The stress test asserts graceful degradation (every order placed or refused with 503, bounded wait), not the normal SLOs

Problem, decision and result

Problem

The stress test found checkout queuing beyond about 90 orders per second, with p95 response time above 3 seconds.

Decision

Add load shedding and rerun the same stress-test profile so the comparison uses the same workload definition.

Comparable run - before

Past about 90 orders/s, checkout queued without bound and p95 exceeded 3 seconds.

Comparable run - after

After load shedding, the same test stayed under 650 ms.

Evidence boundary: The result applies to the demo shop and linked test profile; it is not a capacity guarantee for another deployment.

Test scope and execution approach

Project-specific checks and execution details documented in the repository:

  • Five test types: smoke (gate), load, stress, spike and soak; soak samples the server's memory every 10 s
  • Finding: past about 90 orders/s checkout queued without limit (p95 over 3 s and rising); fixed with load shedding, the slowest checkout is now 624 ms
  • Regression demo: a 300 ms slower checkout passes every functional check but fails the checkout SLO (p95 425 ms vs 400 ms)
  • Markdown result table on every CI run page; HTML dashboard and JSON as artifacts
  • Design notes and 78 interview questions on performance testing and k6, linked to the code (Markdown + PDF)

Known limitations

  • Shared CI runners are noisy: the CI sizes catch regressions; capacity numbers need dedicated load generators and a production-like environment
  • The app under test is a demo with simulated latencies
  • The measured limit and load-shedding result apply to the repository demo shop and the linked stress-test profile.

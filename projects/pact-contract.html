Pact Contract Testing

Consumer-driven contracts with Pact V4: matchers and provider states with parameters on the consumer side, JUnit 5 verification of the real Spring Boot app with pending and WIP pacts, and publish, can-i-deploy and record-deployment in GitHub Actions.

Technologies: Pact, TypeScript, Java 17, Spring Boot, Docker, GitHub Actions

Source codeREADME and setupWorkflow historyReport or image

Problem and purpose

Shows how two teams can change and deploy their services independently without an end-to-end environment: the consumer writes down what it needs, the provider proves it delivers that, and the broker answers before every deployment whether the versions fit together. Two languages on purpose: the teams share only the contract.

Engineering decisions and tradeoffs

  • The consumer's contract tests run its real HTTP client, so the contract records what the code really sends
  • Only the fields the consumer uses are in the contract, with type and format matchers; the provider may change the rest
  • Provider states with parameters ("a product exists" with id, price and stock) instead of one state per example
  • The contract accepts any Bearer token; the provider's request filter injects a valid one, but leaves the no-token case alone
  • Pending and WIP pacts: a consumer's new expectation never breaks the provider's build; can-i-deploy blocks the consumer instead
  • The breaking-change demo checks why can-i-deploy said no, so a no for another reason cannot pass as success

Known limitations

Known limitations

  • One consumer; message (event) contracts are not included yet
  • The broker in CI is new for every run and has no authentication (a shared broker needs both)

Possible next steps

  • A second consumer and a message pact for an event
  • A broker webhook that starts the provider verification, and can-i-merge on pull requests

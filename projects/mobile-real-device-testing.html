Mobile Testing on Real Devices (BrowserStack)

Tests on real phones in BrowserStack's device cloud: a mobile-first shop on Safari on a real iPhone and Chrome on a real Android phone (Selenium, BrowserStack Local tunnel), and a native iOS app on a real iPhone (Appium XCUITest). Developed for free on Chrome mobile emulation; every real-device minute planned and counted.

View source code View documentation View latest CI runs View test report

Purpose

Emulators and desktop browsers miss what only a phone has: the real Safari engine, the on-screen keyboard, touch, OS behaviour. This project runs the same suite on emulation and on real devices, and shows how a real-device-only failure was diagnosed with a probe instead of guesswork.

Technology stack

AreaTools
WebSelenium 4 against PocketShop (in the repository), served by the JDK HTTP server, reached by real devices through BrowserStack Local
NativeAppium Java client 11, XCUITest, BrowserStack's sample iOS app on App Automate
DevicesiPhone 16 (iOS 18, Safari and native), Samsung Galaxy S24 (Android 14, Chrome), Chrome mobile emulation
TestsTestNG, Java 21: 13 web tests, 5 native tests
CIGitHub Actions: emulation on every push; real devices only when started by hand, so a push never spends minutes

Key engineering decisions

  • Develop on Chrome mobile emulation; spend device minutes only to prove and to diagnose
  • One device session per suite; state reset through localStorage instead of new sessions
  • Native locators from one discovery session (element trees saved to files): no trial and error on the device
  • A probe instead of a guess when the real Android phone failed
  • An app in the repository reached through a tunnel: no bot checks, no shared environment

Implemented features

  • Phone checks: viewport meta, one column, no sideways scrolling, hamburger menu, 44 px touch targets
  • Keyboards and autofill per field, and 16 px inputs against the iOS Safari zoom-on-focus problem
  • Found only on the real Android phone: with the keyboard open, the automated tap landed on the page, not the button
  • Native iOS: text on the real keyboard, a native alert, a web view, tab navigation
  • About 9.5 Automate and 1.3 App Automate minutes used for everything, including the failed tries
  • Design notes and 52 interview questions on real-device testing (Markdown + PDF)

Setup and execution

mvnw.cmd test                     :: web suite, Chrome mobile emulation (free)
mvnw.cmd test -Dtarget=iphone     :: web suite, Safari on a real iPhone
mvnw.cmd test -Dtarget=android    :: web suite, Chrome on a real Android phone
mvnw.cmd test -Dsuite=app         :: native app, real iPhone

Sample test results

CI workflow

On every push: the web suite in headless Chrome mobile emulation. Real devices through "Run workflow" with a choice of iPhone web, Android web, iPhone app or all, using repository secrets.

Known limitations and future improvements

Limitations

  • Two phones; a product would choose its device matrix from analytics
  • The native part uses BrowserStack's sample app: the Sauce Labs demo app could not be re-signed for BrowserStack's devices

Next steps

  • A device matrix in parallel sessions
  • Performance on a throttled network profile

Problem and purpose

Shows a Python test stack for one application with a web UI and a REST API on the same backend: the public Expand Testing Notes app. The API carries most of the checks, the browser checks what a user sees, and hybrid tests check that the two sides agree.

My contribution

I built and maintain this public project, including the framework or test harness, its documentation, and the execution evidence linked here.

Engineering decisions and tradeoffs

  • Every test registers its own user through the API and deletes it in teardown, so tests are independent and safe with pytest-xdist on a shared public site
  • UI tests log in by putting the API token into localStorage before the page loads; the login form itself is tested once
  • The API client returns raw responses and never asserts, so the same client serves positive and negative tests
  • pydantic models with extra="forbid": an added or renamed field fails a test at once instead of passing silently
  • Page objects hold data-testid locators and actions; tests assert with Playwright's retrying expect, with no sleeps anywhere
  • Demo tests that fail, skip and xfail on purpose carry their own marker and stay out of normal runs

Local setup and execution

python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
playwright install chromium firefox webkit
pytest -n 4                              # all 46 tests
pytest -m api                            # API only
pytest -m "ui or e2e" --browser firefox  # browser tests on Firefox
pytest -m demo                           # report demo: 2 failed, 1 skipped, 1 xfailed

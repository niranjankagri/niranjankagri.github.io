Problem and purpose

Example-based tests only check the cases someone thought of. Property-based tests generate the inputs, so they find the case nobody wrote down, and shrinking turns a long random failure into a regression example a person would write. This complements the PIT project: PIT changes the code, property-based testing changes the inputs.

Architecture

generator ──► 1,000 inputs ──► property (a rule for every input)
                                 └ fails ──► shrink to the smallest failing input ──► print it with the seed

Engineering decisions and approach

  • Buggy first drafts live in test code only, so the shrinking demos never ship
  • An oracle that is obviously right: a BitSet of busy minutes for the calendar
  • A stateful model check runs random command sequences on the real ledger and a two-field model
  • Bad input must fail in one documented way, never with an index or memory error
  • Only shrunk values from single-source generators are pinned, because mixed generators shrink differently per JDK

Test scope and execution approach

Project-specific checks and execution details documented in the repository:

  • Four first drafts shrunk to minimal examples: 1 cent between 2 people, two touching minutes, one release call
  • Round-trip property for any Unicode text, including emoji and the separator character
  • Generators with edge values mixed in, such as amounts of 0, 1, 99 and 100 cents
  • A failure is reproducible with its seed
  • Documented limits of the unmaintained library, measured on two JDKs

Known limitations

  • QuickTheories 0.26 is from 2019 and no longer maintained
  • Generators built with mix() can stop shrinking early, at a point that depends on the JDK
  • Numbers shrink close to a boundary, not always onto it; the exact boundary is then written as an example test
  • QuickTheories 0.26 is no longer maintained, and shrinking with mixed generators depends on the JDK (documented in the repository).

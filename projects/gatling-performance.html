Problem and purpose

A load test can look healthy because of how it sends the load. Here the closed model (40 concurrent users) reported p95 0.5 s, while the open model (100 new users per second) showed the real queue: p95 16 s, at the same throughput. The project also proves its SLO gate: CI runs the load test against a payment provider five times slower and expects the build to fail.

Architecture

Simulation (users, arrival, SLOs)
  └─ Journey (what one user does)
       └─ Endpoint objects: AuthApi, CatalogApi, OrderApi (request + checks)
            └─ Feeders (100 customers from CSV, random baskets)

Technology and tools

AreaTools
TestsJava 21, Gatling 3.16.0 with the Maven plugin: smoke, load, regression, capacity, closed and open simulations
ApplicationA shop API in the repository (JDK HTTP server, virtual threads) with a payment provider limited to about 80 orders per second
GateGatling assertions for success rate and percentiles; a missed SLO fails Maven and the CI job
CIGitHub Actions: smoke, load and the regression demo on every push; closed, open and capacity weekly and on demand

Engineering decisions and approach

  • Open workload model for independent users, closed only for a fixed pool of clients
  • Endpoint objects, the API version of page objects, chained into journeys
  • Content checks, not only status codes: the order read back has the SKU and total that were ordered
  • The API counts orders itself, so every order Gatling placed is confirmed on the server side
  • A regression demo that must fail, to prove the gate works

Test scope and execution approach

Project-specific checks and execution details documented in the repository:

  • Closed vs open model at the same throughput: p95 510 ms vs 16,323 ms for placing an order
  • Capacity steps from 20 to 110 orders per second; the knee is just under 80, as the payment limit predicts
  • Load test: 4,040 requests, 0 failed, p95 52 ms against an SLO of 300 ms
  • Regression: p95 8,507 ms with 100% success, so an error-rate check alone would have passed it
  • Correlation of the login token and order id, and a summary script for the CI job summary

Known limitations

  • Load generator and API share one machine, locally and in CI: good for comparing models and catching regressions, not for absolute capacity
  • The API is deliberately tiny, so every wait measured is the payment queue
  • No distributed load generation
  • Load generator and API share one machine; the numbers compare models and catch regressions, not the capacity of a real system.
